## Instalação

O djLint precisa do [Python](https://python.org) 3.11 ou mais recente e é publicado no [PyPI](https://pypi.org/project/djlint/).

<Tabs>
<TabItem label="uv">

Com o [uv](https://docs.astral.sh/uv/), adicione-o ao seu projeto como dependência de desenvolvimento:

```bash
uv add --dev djlint
```

Ou instale-o como uma ferramenta independente:

```bash
uv tool install djlint
```

</TabItem>
<TabItem label="pip">

```bash
pip install djlint
```

</TabItem>
<TabItem label="pipx">

Com o [pipx](https://pipx.pypa.io/):

```bash
pipx install djlint
```

</TabItem>
<TabItem label="Homebrew">

Com a [fórmula do Homebrew](https://formulae.brew.sh/formula/djlint) mantida pela comunidade, no macOS ou no Linux:

```bash
brew install djlint
```

</TabItem>
<TabItem label="npm">

:::caution[Atenção]
O pacote npm é apenas um wrapper. O script de instalação dele executa o pip com o `python3` que estiver no PATH do seu sistema e instala a versão do djLint correspondente àquela release do npm, o que pode substituir um djLint mais novo por um mais antigo. O npm não vai gerenciar nem desinstalar o pacote de fato, então prefira o pip sempre que puder.
:::

```bash
npm i djlint
```

</TabItem>
</Tabs>

Para executar o djLint no seu editor ou a cada commit, consulte [Integrações](/pt-br/docs/integrations/) e [pre-commit](/pt-br/docs/integrations/#pre-commit).

:::note[Observação]
Se o comando `djlint` não for encontrado, adicione a pasta em que ele foi instalado ao seu PATH. Quando o djLint está instalado em um ambiente Python, `python -m djlint` com o Python desse ambiente também o executa.
:::

## Primeira execução

Passe ao djLint a pasta com os seus templates e defina `--profile` com a sua linguagem de template. O perfil decide quais regras do linter rodam e como a sintaxe dos templates é formatada. Para um projeto Django:

Faça o lint dos templates (esse é o modo padrão, então dá para omitir `--lint`):

```bash
djlint templates --lint --profile=django
```

Veja o que a formatação mudaria. Com `--check`, o djLint mostra um diff e não mexe nos arquivos:

```bash
djlint templates --check --profile=django
```

Formate os arquivos no próprio lugar:

```bash
djlint templates --reformat --profile=django
```

A opção [`profile`](/pt-br/docs/configuration/#profile) lista todos os perfis. Cada linguagem de template também tem uma página própria, por exemplo [Django](/pt-br/docs/languages/django/), [Jinja](/pt-br/docs/languages/jinja/) ou [Handlebars](/pt-br/docs/languages/handlebars/), que mostra como definir o perfil em um arquivo de configuração para não precisar passá-lo toda vez.

Se você adicionou o djLint ao projeto com `uv add --dev`, ele fica no ambiente do projeto: coloque `uv run` antes dos comandos, por exemplo `uv run djlint templates --lint --profile=django`.

## Usando caminho ou stdin

O djLint funciona com um caminho ou com o stdin.

Executando com um caminho:

```bash
djlint /path/to/templates --lint
```

Ou com um arquivo específico:

```bash
djlint /path/to/this.mustache --lint
```

Ou com o stdin:

```bash
echo "<div></div>" | djlint -
```

O stdin também pode ser usado para reformatar código. A saída será apenas o código formatado, sem mensagens.

```bash
echo "<div></div>" | djlint - --reformat
```

Saída:

```html
<div></div>
```

Ao ler do stdin, o djLint não tem um caminho real para comparar com `per-file-ignores` nem para mostrar nas mensagens, então usa `-` por padrão. Passe `--stdin-filename` para informar ao djLint o caminho real do conteúdo recebido pelo pipe, por exemplo quando uma integração com editor envia o conteúdo de um arquivo pelo pipe ao salvar.

```bash
echo "<div></div>" | djlint - --stdin-filename templates/index.html
```

## Códigos de saída

| Código | Significado                                                                                                                                                                                                                            |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`    | Tudo o que você pediu para o djLint verificar está limpo, ou todos os arquivos encontrados foram ignorados pela sua configuração.                                                                                                      |
| `1`    | O djLint encontrou erros de lint ou arquivos que precisam ser reformatados. `--warn` relata esses casos como avisos e, em vez disso, sai com `0`.                                                                                      |
| `2`    | O djLint não verificou o que você pediu: os caminhos não corresponderam a nenhum arquivo, um arquivo não pôde ser lido (não está em UTF-8, ou falta permissão), a linha de comando ou a configuração era inválida, ou o djLint falhou. |

Somente o código `1` significa que o djLint analisou seus templates e não gostou do que encontrou, então um pipeline consegue distinguir uma verificação que falhou de uma execução que não verificou nada, como uma com um caminho errado ou com uma `--extension` que não corresponde mais a nada.

Arquivos que o djLint encontrou e depois ignorou de propósito, por meio de `exclude`, `extend_exclude`, `use_gitignore` ou `require_pragma`, não são um erro, e é isso que permite que `exclude` funcione com o pre-commit. Se um caminho sem templates for normal no seu pipeline, desative o código `2` com [`allow_empty_input`](/pt-br/docs/configuration/#allow-empty-input):

```bash
djlint /path/to/templates --lint --allow-empty-input
```
