## Instalacja

djLint wymaga [Pythona](https://python.org) 3.11 lub nowszego i jest opublikowany w [PyPI](https://pypi.org/project/djlint/).

<Tabs>
<TabItem label="uv">

Za pomocą [uv](https://docs.astral.sh/uv/) dodaj go do projektu jako zależność deweloperską:

```bash
uv add --dev djlint
```

Możesz też zainstalować go jako samodzielne narzędzie:

```bash
uv tool install djlint
```

</TabItem>
<TabItem label="pip">

```bash
pip install djlint
```

</TabItem>
<TabItem label="pipx">

Za pomocą [pipx](https://pipx.pypa.io/):

```bash
pipx install djlint
```

</TabItem>
<TabItem label="Homebrew">

W systemie macOS lub Linux za pomocą rozwijanej przez społeczność [formuły Homebrew](https://formulae.brew.sh/formula/djlint):

```bash
brew install djlint
```

</TabItem>
<TabItem label="npm">

Pakiet npm ma własnego Pythona, więc potrzebuje tylko Node.js 16.9 lub nowszego. Ma kompilacje dla Linuksa, macOS i Windows na x64 i Arm64. Dodaj go do projektu jako zależność deweloperską:

```bash
npm i -D djlint
```

Potem uruchamiaj go przez `npx djlint`, na przykład `npx djlint . --lint`.

</TabItem>
</Tabs>

Aby uruchamiać djLint w edytorze lub przy każdym commicie, zobacz [Integracje](/pl/docs/integrations/) i [pre-commit](/pl/docs/integrations/#pre-commit).

:::note[Uwaga]
Jeśli polecenie `djlint` nie zostanie znalezione, dodaj do PATH folder, do którego je zainstalowano. Gdy djLint jest zainstalowany w środowisku Pythona, uruchomi go też `python -m djlint` wywołane Pythonem z tego środowiska.
:::

## Pierwsze uruchomienie

Wskaż djLint folder z szablonami i ustaw w `--profile` swój język szablonów. Od profilu zależy, które reguły lintera zostaną uruchomione i jak zostanie sformatowana składnia szablonów. Dla projektu w Django:

Zlintuj szablony (lintowanie to tryb domyślny, więc `--lint` możesz pominąć):

```bash
djlint templates --lint --profile=django
```

Sprawdź, co zmieniłoby formatowanie. Z `--check` djLint wypisuje diff i nie rusza plików:

```bash
djlint templates --check --profile=django
```

Sformatuj pliki w miejscu:

```bash
djlint templates --reformat --profile=django
```

Wszystkie profile wymienia opcja [`profile`](/pl/docs/configuration/#profile). Każdy język szablonów ma też własną stronę, na przykład [Django](/pl/docs/languages/django/), [Jinja](/pl/docs/languages/jinja/) albo [Handlebars](/pl/docs/languages/handlebars/), na której widać, jak ustawić profil w pliku konfiguracyjnym, żeby nie podawać go za każdym razem.

Jeśli djLint został dodany do projektu przez `uv add --dev`, znajduje się w środowisku projektu: poprzedzaj polecenia `uv run`, na przykład `uv run djlint templates --lint --profile=django`.

## Ścieżka a stdin

djLint działa ze ścieżką lub ze standardowym wejściem (stdin).

Uruchomienie ze ścieżką:

```bash
djlint /path/to/templates --lint
```

Albo z konkretnym plikiem:

```bash
djlint /path/to/this.mustache --lint
```

Albo ze stdin:

```bash
echo "<div></div>" | djlint -
```

Stdin można też wykorzystać do przeformatowania kodu. Na wyjściu pojawi się wtedy wyłącznie sformatowany kod, bez komunikatów.

```bash
echo "<div></div>" | djlint - --reformat
```

Wynik:

```html
<div></div>
```

Przy czytaniu ze stdin djLint nie ma prawdziwej ścieżki, którą mógłby dopasować do `per-file-ignores` lub pokazać w komunikatach, więc domyślnie używa `-`. Przekaż `--stdin-filename`, aby podać djLint prawdziwą ścieżkę przekazywanej treści, na przykład gdy integracja z edytorem przesyła przy zapisie zawartość pliku.

```bash
echo "<div></div>" | djlint - --stdin-filename templates/index.html
```

## Kody wyjścia

| Kod | Znaczenie                                                                                                                                                                                                                           |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0` | Wszystko, co djLint miał sprawdzić, jest w porządku albo każdy znaleziony plik został pominięty zgodnie z konfiguracją.                                                                                                             |
| `1` | djLint znalazł błędy lintowania lub pliki wymagające przeformatowania. Przy `--warn` są one zgłaszane jako ostrzeżenia, a djLint kończy działanie z kodem `0`.                                                                      |
| `2` | djLint nie sprawdził tego, o co go poproszono: ścieżki nie pasowały do żadnych plików, nie udało się odczytać pliku (nie jest w UTF-8 albo brak uprawnień), wiersz poleceń lub konfiguracja były nieprawidłowe albo djLint zawiódł. |

Tylko kod `1` oznacza, że djLint przejrzał twoje szablony i nie spodobało mu się to, co znalazł, więc potok CI odróżni nieudane sprawdzenie od uruchomienia, które niczego nie sprawdziło, na przykład z błędną ścieżką albo z `--extension`, które już do niczego nie pasuje.

Pliki, które djLint znalazł, a potem celowo pominął z powodu `exclude`, `extend_exclude`, `use_gitignore` lub `require_pragma`, nie są błędem i dzięki temu `exclude` działa w pre-commit. Jeśli w twoim potoku CI ścieżka bez szablonów jest czymś normalnym, wyłącz kod `2` opcją [`allow_empty_input`](/pl/docs/configuration/#allow-empty-input):

```bash
djlint /path/to/templates --lint --allow-empty-input
```
